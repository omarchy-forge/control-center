# Omaforge Local Control Center

Start, stop, restart, and watch logs for one local project's development
services (dev servers, workers, local backends) — from the Omarchy bar,
without a terminal.

This project was generated by Omarchy Forge as a bar widget with a
keyboard-accessible popout, then implemented against
[`FORGE_SPEC.md`](FORGE_SPEC.md); read that file for the full, itemized
specification and the requirement-inventory table tracing every control back
to the confirmed product reference.

## Features

- Shows a project's name, git branch, and the status of every service listed
  in its `.omaforge/services.json`.
- Start, stop, or restart an individual service, or Run all / Stop all.
- Live, in-memory log view (last 500 lines) per service, with a Clear action.
- Adapts to top, bottom, left, and right bar orientations through official UI
  components, and uses Omarchy theme, spacing, typography, surface, and
  border tokens.
- Full keyboard operation (see "Usage" below) with a visible focus state.
- Loading, ready, empty, and error states, including deterministic fictional
  demo states.

## One plugin instance per project

This widget monitors **one project directory per instance** (set via the
"Project directory" setting). To monitor several projects, enable this
widget more than once (`allowMultiple: true`) and give each instance a
different project directory. This is a deliberate design choice — see
`FORGE_SPEC.md`'s requirement-inventory row 3 for why an in-popout
project-switcher was not built.

## Install

Review the source, then install this local checkout:

```bash
omarchy plugin add "$PWD" --enable
```

Plugins execute unsandboxed in the long-lived Omarchy Shell process. Only
enable code you trust — this one starts and stops local processes on your
behalf once you configure it (see "Privacy and security" below).

## Configuration

Two settings, editable from Omarchy's plugin settings UI:

- `projectPath` (type `path`, default empty) — the local git project
  directory this instance monitors. Leave unset and the widget shows a
  guided Empty state instead of an error. Add another instance of this
  widget (`allowMultiple: true`) for each additional project.
- `refreshIntervalSec` (10–3600, default 60) — how often the git-branch and
  service-config status is re-checked; see `FORGE_SPEC.md` "Refresh triggers
  and interval". Omarchy persists both settings inline in its shell
  configuration, the same mechanism every plugin's settings use.

The services shown and controlled come from `.omaforge/services.json` inside
`projectPath` — see "Configuring services" below.

## Requirements

- Omarchy 4 with manifest schema 1 and Quickshell plugin support.
- `git` on `PATH`, for the branch label (its absence degrades gracefully;
  see "Privacy and security" below).
- `xdg-open` on `PATH`, only needed if you use the "open service URL" action.
- A project directory containing `.omaforge/services.json` (see below). No
  file means the widget shows a helpful Empty state, not an error.

## Configuring services: `.omaforge/services.json`

Create this file inside the project directory you point the widget at. It is
plain, user-authored JSON — this plugin only ever reads it, never writes it:

```json
{
  "services": [
    { "id": "web", "name": "Web", "command": ["pnpm", "dev"], "url": "http://localhost:3000" },
    { "id": "api", "name": "API", "command": ["uv", "run", "fastapi", "dev"], "cwd": "api", "url": "http://localhost:8000" },
    { "id": "worker", "name": "Worker", "command": ["pnpm", "worker"] }
  ]
}
```

| Field | Required | Notes |
|---|---|---|
| `id` | yes | `[a-zA-Z0-9_-]`, 1–64 chars, unique per file |
| `name` | yes | 1–80 chars, shown as plain text |
| `command` | yes | 1–20 non-empty strings (≤200 chars each) — the literal argv. Never a shell string; the first element must be on `PATH` or an absolute path. |
| `cwd` | no | relative path, resolved inside the project directory; absolute paths and `..` segments that would escape it are rejected |
| `url` | no | must start with `http://` or `https://`; shown next to the service and used by the "open" action — never fetched by the plugin |

At most the first 16 valid entries are shown; invalid entries are skipped
with a note rather than failing the whole file.

## Usage

- Left-click the bar icon to toggle the popout.
- Right-click or middle-click the bar icon to refresh git-branch/config
  status (never starts, stops, or restarts a service).
- Inside the popout:
  - `j`/`k` (or `Down`/`Up`) — move between service rows.
  - `h`/`l` (or `Left`/`Right`) — move focus between the services list and
    the log panel.
  - `Enter` — open the selected service's URL (when the services list has
    focus and the service has one configured).
  - `r` — restart the selected service (services list focused); refresh
    status otherwise.
  - `R` — always refresh git-branch/config status.
  - `x` — stop the selected running service.
  - `Esc` — close the popout.
  - Or use the on-screen Start / Restart / Stop buttons per row, and Run
    all / Stop all.

## Development and testing

```bash
./tests/run
```

After reviewing the plugin code and its local commands, run the opt-in isolated
Quickshell entry-point test on an Omarchy machine:

```bash
./tests/runtime --trust-plugin-code
./tests/runtime --trust-plugin-code --state ready
./tests/runtime --trust-plugin-code --state ready --screenshot /tmp/preview.png
# Or, with Forge on PATH:
omaforge dev . --trust-plugin-code
omaforge dev . --trust-plugin-code --state ready --watch
omaforge screenshot . --trust-plugin-code --state ready --output assets/preview.png
```

The runtime test executes the plugin's QML in a temporary HOME/XDG environment
against the installed Omarchy QML modules. It requires `jq`, `quickshell`, an
active Wayland session, and the standard `setsid` and `timeout` commands. It is
deliberately separate from normal checks and generated CI. The isolated
runtime always starts with an empty `settings` object (no configured project),
so it never touches git, reads a project's `.omaforge/services.json`, or
starts a managed process — the `--state ready|empty|error` path exercises the
same deterministic, fictional, in-memory demo data described in
`demo/fixtures.json`, never real project data.

Screenshot capture uses the template-declared panel content item and never
captures the desktop. It refuses to overwrite an existing PNG. Watch mode
reruns the same isolated harness after project changes and stops on Ctrl-C;
it does not install the plugin into the live shell.

Only after source review and isolated runtime verification, install the local
checkout deliberately, set the "Project directory" setting, and add a
`.omaforge/services.json` to that project. A GitHub push is not required:

```bash
omarchy plugin add "$PWD" --enable
omarchy plugin list
./demo/run ready
./demo/run empty
./demo/run error
```

Saving files below the installed user-plugin directory triggers shell reload in
the verified Omarchy 4 contract. `omarchy-shell shell rescanPlugins` forces a
rescan when needed.

The demo script applies a deterministic fictional in-memory state to the
running plugin instance through Omarchy Shell IPC — it never touches your
real project, its config file, or any process. It does not restart the shell
or modify configuration. `Target not found` means the plugin is not installed
and enabled; use the isolated `tests/runtime --state` path first.

## Update

For a Git-managed installation:

```bash
omarchy plugin update omaforge.control.center
```

## Removal

```bash
omarchy plugin remove omaforge.control.center
```

Removing or disabling the plugin does **not** stop any service processes it
started — stop them yourself first (Stop all, or per-row Stop) if you don't
want them left running.

## Privacy and security

See `FORGE_SPEC.md` for the full, itemized data/command/network/persistence
boundary this was implemented against. Summary:

- **Local commands**: `git -C <projectPath> rev-parse --abbrev-ref HEAD`
  (5s timeout, read-only), a configured service's own `command` array
  (started only on explicit Start/Restart/Run all, run indefinitely until
  explicitly stopped — never auto-started), and `xdg-open <url>` (5s timeout,
  only for a service's own validated `http(s)://` URL). Every command is a
  fixed program invoked with array-form arguments — never a shell string.
- **Network**: none, directly. The plugin never makes an HTTP/socket request
  itself; `xdg-open` only hands the URL to your browser.
- **Persistence**: none beyond Omarchy's own settings storage (the same
  mechanism every plugin's settings already use). No project list, log
  history, or process history is written to disk by this plugin.
- **Failure behavior**: a git failure or timeout on the very first load shows
  a clear error; on a later refresh (once services are already loaded) it
  keeps showing the last known service list/status with an inline warning
  instead of blanking the panel. A service whose program can't be found or
  that exits immediately shows an Error status on its own row without
  affecting the others.
